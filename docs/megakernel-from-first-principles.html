A megakernel is a single GPU kernel that runs a whole program. Instead of launching one kernel per operation (a matmul, a LayerNorm, an attention block) and letting the driver and the hardware scheduler move between them, you launch one kernel whose blocks stay resident for the entire run and pull work from queues in global memory. The GPU stops being a device you send kernels to and becomes a machine that runs its own scheduler.

This post walks through the megakernel in this repository, llm/b200/megakernel/ofa.cu, by rebuilding it from nothing. Every step adds one mechanism and says why the previous version was not enough. Code blocks marked with a file path are verbatim excerpts from the repo; the unmarked ones are minimal versions written for this post to isolate one idea. By the end, every line of the real scheduler should read as obvious.

The prerequisites are the CUDA basics: threads, warps, blocks, shared memory, __syncthreads(), and global-memory atomics. Everything else is introduced where it is needed.

1What a kernel boundary costs

Start with how a training framework normally runs one step of a transformer. Each operation is a kernel. The host enqueues them on a stream, and the stream guarantees that kernel k+1 does not start until every block of kernel k has finished:

for (int step = 0; step < steps; step++)
  for (const Op& op : graph)                        // 278 ops per training step in our GPT
    op.kernel<<<op.ntiles, 256, op.smem, stream>>>(op.args);   // implicit grid-wide barrier between ops

Each boundary costs four things:

  1. The launch itself. A host API call, a few microseconds of driver work, and a command the GPU front end must process. CUDA graphs remove most of the host part but not the rest.
  2. The fill. The new grid's first blocks must be dispatched to SMs, their registers and shared memory allocated, and their pipelines primed with loads before any math happens.
  3. The tail. A grid finishes when its last block finishes. If an op has 256 tasks and the GPU holds 232 blocks at once, the second wave has 24 blocks and the other 208 slots sit idle until they finish. Small ops are mostly tail. In our step, the LayerNorm gamma-gradient reduction has 3 tasks; with a barrier after it, 229 of 232 training slots wait.
  4. The barrier. The next op cannot start any tile, even a tile whose inputs are already final, until every tile of the previous op is done. Work that is independent (a weight gradient and the input gradient of the same layer) is serialized unless someone sets up multiple streams by hand.

Count the boundaries for what this repo runs: one training step of the 12-layer GPT is 278 operations, so 4,000 steps is 1.1 million of them. Serving at batch 1 costs 38 operations per generated token, about 3.1 million for the 81,600 tokens produced alongside training. The framework baselines in the repo, measured with Nsight Systems, issue between 2.2 million and 15.2 million kernels for the same work depending on how they are counted. The megakernel issues one (plus two one-off setup kernels).

A megakernel does not make any individual matmul faster. It removes the boundaries: no launches, no fill after the first, and tails filled with whatever other work is ready. The rest of this post is about how to do that without the program falling apart.

2A kernel that never exits

The first move is to stop mapping blocks to work. In an ordinary kernel, block blockIdx.x computes output tile blockIdx.x and exits. In a persistent kernel you launch only as many blocks as the GPU can hold at once, and each block loops over many units of work:

__global__ void persistent(const Work* w, int ntasks) {
  for (int t = blockIdx.x; t < ntasks; t += gridDim.x)    // grid-stride over tasks
    run_task(w, t);                                        // all 256 threads of the block run one task
}

int occ = 0;
cudaOccupancyMaxActiveBlocksPerMultiprocessor(&occ, persistent, 256, smem_bytes);
persistent<<<num_sms * occ, 256, smem_bytes>>>(w, ntasks);   // exactly one full "wave"

Why exactly one wave? Because later we will make blocks wait for each other. A block that spins waiting for a result occupies its SM slot. If the block it waits for was never scheduled (it is queued behind the spinning blocks), nobody makes progress. As long as every block of the grid is resident at the same time, no block depends on a block that has not started. This is the one hardware assumption the whole design rests on.

The size of that wave comes from the per-SM budgets: registers, shared memory and threads. The B200 build uses 256 threads per block, caps registers at 128 per thread (-maxrregcount=128 and __launch_bounds__(256, 2), so two blocks use the whole 64K-register file), and gives each block 99,200 bytes of dynamic shared memory. Two blocks fit per SM, so the grid is 148 × 2 = 296 blocks:

llm/b200/megakernel/ofa.cuhost, grid sizing

One more consequence of persistence: every task shares one register budget and one shared-memory buffer. A kernel has a single register count, the maximum over every code path it contains, and a single dynamic shared-memory size. The repo checks at compile time that every task body fits in the buffer the GEMM needs:

3Claiming work with one atomic

A static grid-stride loop gives block b tasks b, b+296, b+592 and so on. That is fine when every task takes the same time. Ours do not: a GEMM tile with K = 100,352 (the language-model head's input gradient) runs far longer than a 16-row LayerNorm task. A block that drew several long tasks finishes late while others idle.

The fix is a ticket counter: one unsigned integer in global memory. A block that needs work takes the next number with atomicAdd. Fast blocks simply come back more often.

__global__ void persistent(const Work* w, unsigned* ticket, unsigned total) {
  __shared__ unsigned s_task;
  for (;;) {
    if (threadIdx.x == 0) s_task = atomicAdd(ticket, 1u);  // one atomic per task, by one thread
    __syncthreads();                                       // publish s_task to the block
    const unsigned t = s_task;
    __syncthreads();                                       // all threads read it before thread 0 overwrites it
    if (t >= total) return;
    run_task(w, t);
  }
}

Two details matter. The claim is done by one thread and broadcast through shared memory, because the whole block runs one task cooperatively. And there are two barriers: the first makes the value visible to the block; the second stops thread 0 from racing ahead into the next iteration and overwriting s_task while slower warps are still reading it. You will see exactly this shape in the real job_loop, with s_sel[4] in place of s_task.

A single counter contended by 232 blocks sounds like a bottleneck. It is not, as long as each claim is a single atomicAdd: the L2 atomic unit serializes them, but each takes a few nanoseconds and a task takes microseconds. The trouble starts when a claim needs a retry loop, which is where we will be in section 7.

4Tasks, phases and tickets

We need vocabulary for the work itself.

  • A task is what one block does between two claims: one 128 × 128 output tile of a GEMM, one 64-query tile of one attention head, 16 rows of a LayerNorm, 65,536 elements of AdamW.
  • A phase is a set of independent tasks of the same kind: all 576 tiles of layer 3's QKV projection, for example. Tasks in a phase can run in any order and in parallel.
  • A job is an ordered table of phases plus a dependency list per phase. The training job has 278 phases per step; the decode job has 38 per token.

Every task body in the repo follows the same contract, written down in the library READMEs: it is a __device__ function called by all 256 threads of a block; it never reads blockIdx or gridDim (a task does not know which block runs it); it takes the shared dynamic buffer as a parameter; and it ends with __syncthreads(), so the next task can reuse the buffer. Because of that contract the same GEMM tile code runs unchanged in a stand-alone test kernel and inside the megakernel.

A phase is described by a plain struct that the host fills in and copies to the device:

llm/b200/megakernel/ofa.culines 87–104
enum Kind { K_DATA, K_EMBED, K_LN_FWD, K_GEMM, K_ATT_FWD, K_ATT_PREP, K_ATT_BWD, K_CE, K_CE_MEAN, K_LN_BWD, K_LN_DG, K_EMB_WTE, K_EMB_WPE, K_ADAMW, K_DECODE };

struct PhaseDesc {
  int kind, ntasks, layout, epi;
  int tilesM, i0, i1, i2;
  tg::Args ga;
  const void* p[10];
  size_t n;
};

struct Job {
  int nph, tps, limit, last_ph;                 // phases, tasks per step, #steps, phase whose completion ends a step
  const PhaseDesc* ph;
  const int *prefix, *ntasks, *dep_off, *dep_cnt;
  const int2* deps;                             // (phase, step delta): need done[phase] >= ntasks[phase] * (step + 1 + delta)
  int* done;
  unsigned* ticket;
};

Now the key trick: a ticket is not a task index into one phase; it is a position in the whole run. Lay every task of every phase of every step on one number line, in order. With tps tasks per step and prefix[p] the number of tasks in phases 0 to p−1, ticket g decodes to a step, a phase and a task within the phase:

// tps = tasks per step; prefix[p] = tasks in phases 0..p-1, prefix[nph] = tps
const int step  = g / tps;
const int r     = g - step * tps;               // position inside the step
int ph = 0; while (r >= prefix[ph + 1]) ph++;   // the phase that contains r
const int local = r - prefix[ph];               // task index inside the phase

So one counter enumerates the whole run, 4,000 × 125,287 = 501 million training tickets, in an order the host chose when it built the table. The real code avoids rescanning the prefix array from zero on each claim: thread 0 keeps the last phase it decoded in cph and walks forward from there, since a block's tickets only increase.

For a GEMM phase the task index then maps to an output tile. tilesM is the number of tiles along M, so consecutive tickets walk down a column of tiles, which keeps the shared B-operand panel hot in L2:

llm/b200/megakernel/ofa.culines 139–150
__device__ __noinline__ void run_gemm(const PhaseDesc& d, int local, char* smem) {
  const int tm = local % d.tilesM, tn = local / d.tilesM;
  switch (d.layout * 8 + d.epi) {
    case gemm::NN * 8 + gemm::EPI_BF16:  gtile<gemm::NN, gemm::EPI_BF16>(d, tm, tn, smem); break;
    case gemm::NN * 8 + gemm::EPI_RES:   gtile<gemm::NN, gemm::EPI_RES>(d, tm, tn, smem); break;
    case gemm::NN * 8 + gemm::EPI_GELU:  gtile<gemm::NN, gemm::EPI_GELU>(d, tm, tn, smem); break;
    case gemm::NT * 8 + gemm::EPI_BF16:  gtile<gemm::NT, gemm::EPI_BF16>(d, tm, tn, smem); break;
    case gemm::NT * 8 + gemm::EPI_DGELU: gtile<gemm::NT, gemm::EPI_DGELU>(d, tm, tn, smem); break;
    case gemm::TN * 8 + gemm::EPI_F32:   gtile<gemm::TN, gemm::EPI_F32>(d, tm, tn, smem); break;
    default: break;
  }
}

The runtime switch turns data (the phase descriptor) into a call to one of six compile-time-specialized templates. This is the megakernel's "instruction decode": every opcode the machine can execute has to be compiled into the one binary, and the descriptor selects among them.

5Dependencies without a grid barrier

A ticket counter alone is wrong as soon as phases depend on each other. A block could claim a tile of the attention phase while the QKV projection it reads is half written. In the kernel-per-op world the stream's barrier prevented that. We need something finer: wait only for the phases this task actually reads, and only until they are complete.

Give every phase a completion counter done[ph] in global memory. A block that finishes a task increments its phase's counter. A block about to start a task of phase p checks, for each phase q that p depends on, that done[q] has reached ntasks[q], and sleeps briefly if not.

The subtle part is memory ordering. The counter going up must mean the data is there. Without ordering, the GPU may make the counter's new value visible to another SM before the tile data written just before it. CUDA's memory model gives two tools for this pattern, called release and acquire:

__device__ __forceinline__ int ld_acquire(const int* p) {
  int v;
  asm volatile("ld.acquire.gpu.global.s32 %0, [%1];" : "=r"(v) : "l"(p) : "memory");
  return v;
}

// --- producer: after the task body (all 256 threads wrote parts of the output tile)
__threadfence();                        // each thread: my earlier writes are ordered before my later ones, GPU-wide
__syncthreads();                        // every thread of the block has passed its fence
if (threadIdx.x == 0) atomicAdd(&done[ph], 1);   // publish: one more task of this phase is complete

// --- consumer: thread 0, before the task body
while (ld_acquire(&done[dep]) < ntasks[dep]) __nanosleep(100);
__syncthreads();                        // the rest of the block waits on thread 0, then reads the inputs

Read the producer side as a chain. Each thread's __threadfence() orders that thread's tile writes before anything it does afterwards. The barrier then orders every thread's post-fence point before thread 0's next instruction. So thread 0's atomicAdd comes after all 256 threads' writes, as seen from any SM. On the consumer side, the .acquire load forbids later loads from being performed before it, and the barrier extends that guarantee from thread 0 to the whole block.

Why not just use volatile loads for the counter? Because volatile only stops the compiler from caching the value in a register; it does not stop the hardware from performing the block's subsequent data loads early. An acquire load does. The repo uses volatile only where ordering does not matter, such as the ticket counter in the CAS path and the finished flag.

Caches

Global loads normally go through the SM's L1, and L1 is not coherent across SMs. Inputs produced by another SM in this same launch must not be served from a stale L1 line. The library tasks read such data with cp.async.cg (cache at L2 only), __ldcg, or ld.global.L1::no_allocate. __ldg (the read-only path) appears only for tables that never change during the run, like prefix and deps.

The barrier between ops is gone. In its place is a handshake between exactly the tasks that share data, and a task whose inputs are final can start while unrelated phases are still running.

6Counters that never reset

A training run repeats the same 278 phases 4,000 times. Resetting done[] at the end of each step would need a grid-wide barrier to know when it is safe, which is exactly what we are trying to avoid. The repo never resets them. Phase q's counter keeps climbing: it reads ntasks[q] after step 0, 2 · ntasks[q] after step 1, and so on. A task of step s that needs phase q of the same step waits for

need = ntasks[q] * (step + 1);

That also gives dependencies across steps for free. Each dependency is stored as a pair (phase, delta), and the target becomes ntasks[q] * (step + 1 + delta). With delta = -1 a task waits for phase q of the previous step. At step 0 the target is zero and the check is skipped (need > 0).

This is how step s+1 begins before step s has fully ended. The AdamW phase for layer l depends only on layer l's gradient phases, so the optimizer for layer 11 can run while the backward pass is still working through the lower layers. In the other direction, layer l's first forward phase of the next step carries the dependency (adamw Ll, -1) and nothing else from the previous step, so it waits for that one layer's update, not for the whole optimizer pass. No global "step finished" event stands between two steps.

The Builder on the host records dependencies in exactly this form, with a flat deps array and per-phase offsets so the device can walk them with no pointers:

llm/b200/megakernel/ofa.culines 352–362
struct Builder {
  std::vector<PhaseDesc> ph; std::vector<int> dep_off, dep_cnt, ntasks; std::vector<int2> deps; std::vector<std::string> names;
  int add(const std::string& name, PhaseDesc d, std::vector<int> after, std::vector<int2> prev = {}) {
    dep_off.push_back((int)deps.size());
    for (int a : after) if (a >= 0) deps.push_back(make_int2(a, 0));
    for (auto p : prev) deps.push_back(p);
    dep_cnt.push_back((int)deps.size() - dep_off.back());
    ph.push_back(d); ntasks.push_back(d.ntasks); names.push_back(name);
    return (int)ph.size() - 1;
  }
};

Since a phase can only depend on phases that were added before it (add returns the new index, and you can only pass indices you already have), the phase table is in topological order by construction. That property is about to matter a lot.

7Why it cannot deadlock

Combine the ticket with the dependency wait and an obvious worry appears. Block A claims ticket 1,000 and starts waiting on a phase whose last task is ticket 990. Block B holds ticket 990 but is itself waiting on something. Can the waits form a cycle?

They cannot, for two reasons that the design arranges deliberately:

  1. Every dependency points to a lower ticket. Phases within a step are in topological order, and cross-step dependencies use delta = -1, which points into the previous step's range. So a task only ever waits on tasks with smaller ticket numbers.
  2. Every claimed ticket belongs to a running block. Tickets are handed out in increasing order, so if ticket 1,000 has been claimed then 0 to 999 have been claimed too, each by a block that is resident (that is the one-wave rule from section 2).

Now take the lowest ticket whose task has not finished. Everything it depends on has a lower number, so it has finished. That task is therefore running, not waiting, and will complete. Then the next-lowest unfinished ticket is in the same position. By induction every claimed task completes. No cycle is possible because waits only point downward.

This argument is what allows the cheapest possible claim: an unconditional atomicAdd, taken before checking whether the task is ready. The repo did not start there. The first version only claimed tickets that were already ready, with a compare-and-swap:

llm/b200/megakernel/ofa.culines 260–281 (the CAS path, kept under #else)
for (;;) {
  if (job_id == 1 && ld_vol(C.finished)) { res = -2; break; }
  const unsigned g = ld_vol(J.ticket);
  if (g >= total) { res = -2; break; }
  step = (int)(g / (unsigned)J.tps); const int r = (int)(g - (unsigned)step * (unsigned)J.tps);
  if (r < __ldg(J.prefix + cph)) cph = 0;
  while (r >= __ldg(J.prefix + cph + 1)) cph++;
  ph = cph;
  bool ready = (step == rstep && ph == rph);
  if (!ready) {
    ... check every dependency with ld_acq ...
  }
  if (!ready) { __nanosleep(job_id == 1 ? 100 : 200); continue; }
  if (atomicCAS(const_cast<unsigned*>(J.ticket), g, g + 1) == g) { local = r - __ldg(J.prefix + ph); break; }
}

This is correct, and it never parks a block on an unready task. But every block reads the same counter, and only one of the blocks that read value g wins the CAS; all the others go around again. The research log measured the result: the CAS loop serialized at about 1.9 claims per microsecond. At 125,000 tasks per step that is 66 ms of pure claiming per step, longer than the step itself. Switching to fetch-add made the whole training loop about twice as fast (llm/megakernel/MERGE.md, item 1).

Every piece of the previous sections is here: the one-thread claim, the ticket decode with the phase cache, the (phase, delta) targets, the acquire loads, the sleep. One more optimization is visible: rstep and rph remember the last (step, phase) this block found ready. Counters only grow, so once a phase's dependencies are satisfied for a given step they stay satisfied, and a block that claims several tasks of the same phase in a row checks only once. The decode job (job 1) also polls a finished flag, because it has no natural end; it stops when training does.

The return value of atomicAdd is used to detect the last task of a step without another counter: if the old value was one less than the target, this block just completed the step. It stamps the time from %globaltimer (a GPU-wide nanosecond clock), and after the final step it raises finished, which stops the decode and Doom loops. The profiler is just more atomics: per-phase busy time and the first-start / last-end of each phase at one chosen step.

8Barriers against counters, simulated

The scheduler is complete, so it is worth seeing what it buys. Below is a toy training step with the same shape as the real one: three layers of forward, a head, a backward pass where each layer has an input-gradient chain (dX) and an independent weight-gradient branch (dW), and one AdamW phase per layer. The next step's layer l forward depends on layer l's AdamW of the previous step, as in section 6.

The top chart runs it as one kernel per phase: phases in stream order, a launch gap between them, every phase waiting for the previous one. The bottom chart runs the same tasks, with the same durations, through the megakernel's rules: fetch-add tickets in table order, per-phase counters, no barriers. Three things to try. Set the launch gap to zero: the megakernel still wins, because the remaining gain is the tails being filled by the dW branch and AdamW. Drop the blocks to 4: phases have more tasks than blocks, tails shrink relative to the work, and the gap narrows. Raise the jitter: per-phase barriers wait for the slowest task, and the dynamic claim hides it. These are the same effects the real kernel gets on a much larger graph.

What the toy hides is that the megakernel pays for claims and waits it does not show, and that the real tasks contend for memory bandwidth. Section 15 has the measured numbers.

Notice what is not a phase. The residual add is fused into the epilogue of the output projections (EPI_RES); the GELU is fused into the up-projection (EPI_GELU, which also saves the pre-activation for backward). The pv(1) on the first LayerNorm is a placeholder for the cross-step dependency on this layer's AdamW, patched in once the AdamW phases exist.

Every activation and gradient buffer is per layer (ln1[l], qkv[l], dqkv[l], ...). That costs memory (14.2 GB used on the B200) but removes write-after-read hazards: if layer 3 and layer 4 shared a scratch buffer, a fast task of layer 4 could overwrite data a slow task of layer 3 is still reading, and you would need extra dependency edges to prevent it. With private buffers the only edges are the true data dependencies.

10The task bodies

The scheduler gives each task a block of 256 threads, a shared-memory buffer and nothing else. The task libraries live in llm/gemm, llm/attention, llm/elementwise and llm/decode, each with its own stand-alone test against a PyTorch reference.

GEMM: one 128 × 128 tile

The A100 GEMM (llm/gemm/gemm.cuh) is a conventional tensor-core tile written for this contract. Eight warps in a 2 × 4 arrangement each own a 64 × 32 piece of the output, computed with mma.sync.m16n8k16 in bf16 with fp32 accumulation. Operands stream through a 4-stage cp.async pipeline with K-chunks of 32, stored in an XOR-swizzled shared-memory layout so that both the async copies and the ldmatrix reads are free of bank conflicts:

llm/gemm/gemm.cuhtile load into swizzled shared memory
//  K-contiguous  (tile stored [mn][k], 64 B rows): byte = mn*64 + ((k/8) ^ ((mn>>1)&3))*16 + (k%8)*2
//  MN-contiguous (tile stored [k][mn], 256 B rows): byte = k*256 + ((mn/8) ^ (k&7))*16 + (mn%8)*2
template <bool KC>
__device__ __forceinline__ void load_tile(uint32_t sbase, const bf16* g, int ld, int mn0, int k0, int tid) {
#pragma unroll
  for (int i = 0; i < 2; i++) {
    int c = tid + i * THREADS;
    if (KC) {
      int row = c >> 2, kc = c & 3;
      cp_async16(sbase + row * 64 + ((kc ^ ((row >> 1) & 3)) << 4), g + (size_t)(mn0 + row) * ld + k0 + kc * 8);
    } else {
      int k = c >> 4, mc = c & 15;
      cp_async16(sbase + k * 256 + ((mc ^ (k & 7)) << 4), g + (size_t)(k0 + k) * ld + mn0 + mc * 8);
    }
  }
}

Three layouts cover every matmul in training: NN for forward linears (Y = XW), NT for input gradients (dX = dY WT) and for the tied logits, and TN for weight gradients (dW = XTdY, reducing over the 4,096 tokens). Five epilogues fuse the elementwise work that would otherwise be separate phases:

EpilogueComputesUsed by
EPI_BF16C = accQKV, logits, dX GEMMs
EPI_RESC = acc + R (R may alias C)attention output and MLP down projections
EPI_GELUaux = acc; C = gelu(aux)MLP up projection
EPI_DGELUC = acc · gelu′(aux)backward through the MLP activation
EPI_F32C (+)= acc in fp32weight gradients, written straight into the fp32 gradient buffer

The GEMM has no atomics and a fixed reduction order over K, so it is deterministic. That is true of every task in the repo: there are no floating-point atomics anywhere in training. The practical payoff is large. The loss curve is bit-identical whether the kernel runs with 85 or 116 training SMs, with or without Doom, with the per-layer AdamW overlap on or off, and with the mma.sync or tcgen05 GEMM. When you change the scheduler you can diff the loss file and know immediately whether you broke synchronization.

Attention

Attention is flash-style: a forward task is one (sequence, head, 64-query tile), with an online softmax over 64-key blocks, and it saves the log-sum-exp for backward. The backward is split into a prep phase (D = rowsum(dO ∘ O)) and one phase holding two task kinds: the first 768 tasks each compute dK, dV for one key tile, the next 768 each compute dQ for one query tile. Splitting dQ out this way means no task has to accumulate into another task's output, which is what lets the backward avoid atomics.

Elementwise

LayerNorm forward and backward take 16 rows per task; cross-entropy takes 4 rows of 100,352 logits each and writes per-row losses that a 1-task phase averages; AdamW takes 65,536 parameters per task, updates the fp32 master weights, the two moments, and writes the bf16 copy that the GEMMs (and the server) read. LayerNorm's gamma gradient is a two-level reduction: each backward task writes a partial sum for its 16 rows, and a 3-task phase reduces the 256 partials per column in a fixed order.

One binary, one register budget

Every one of these bodies is compiled into the same kernel. The register allocator assigns one count to the whole kernel, so the leanest LayerNorm task runs with the GEMM's 128 registers. run_gemm is marked __noinline__ so its large body is compiled as a separate function, which keeps the scheduler loop from inheriting its register pressure and spills.

11Three programs, one grid

So far there is one job. The kernel runs three: training, serving and Doom. The simplest way to share a GPU between jobs inside one kernel would be one queue with priorities: always take a Doom task if one is ready, else a decode task, else training. The small demo in a100-demo/ does exactly that. It does not scale to this model, for one reason: a task cannot be preempted. Once a block starts a training GEMM tile with K = 100,352 it runs to the end. A Doom frame that becomes due in the meantime waits. With long tasks, priorities alone cannot give a frame deadline or a steady token rate.

So the LLM kernel partitions the GPU by physical SM. Each block reads the hardware register %smid and picks its role:

llm/b200/megakernel/ofa.culines 316–326, the kernel entry
__global__ void __launch_bounds__(256, OFA_BLOCKS_PER_SM) ofa_kernel(const Ctx C) {
  extern __shared__ __align__(128) unsigned char dsm[];
  unsigned hw; asm volatile("mov.u32 %0, %%smid;" : "=r"(hw));
  const int smid = C.smid_rank ? C.smid_rank[hw] : (int)hw;                          // dense rank of this SM
  char* smem = reinterpret_cast<char*>(dsm);
  const int isms = C.use_decode ? C.infer_sms : 0, dsms = C.use_decode ? C.doom_sms : 0;
  if (smid < isms) job_loop(C, C.dec, 1, smem);
  else if (smid < isms + dsms) { if (C.dm.on) doom_loop(C.dm); else return; }       // Doom's partition
  else if (smid < isms + dsms + C.train_sms) job_loop(C, C.train, 0, smem);
  else return;                                                                       // SMs beyond the requested train share stay idle
}

Why %smid and not blockIdx.x? The hardware does not promise which SM block i lands on. Partitioning by blockIdx could put a serving block and a training block on the same SM, where they compete for the SM's issue slots, L1 and shared-memory bandwidth, and the serving latency would depend on what training happens to be doing. Partitioning by %smid puts both blocks of an SM in the same job. The two roles never share an SM.

%smid has one wrinkle: it is a hardware ID, and on a part with disabled SMs the IDs may not be contiguous. The host runs a probe kernel with the same launch shape first; each block records its %smid in a bitmap and spins for about 2 ms so that every block is resident at once and every SM gets its share. If the IDs seen are not exactly 0 to n−1, the host uploads a table mapping hardware ID to dense rank, which is the smid_rank lookup above. On the B200 used here the probe saw 148 SMs with IDs 0 to 147, so the table was not needed.

Within the training partition, the two jobs that use job_loop each get their own Job struct, so their own ticket counter and their own done[] array. They share nothing except the bf16 weights.

12Serving from weights that are still training

The decode job generates text one token at a time, batch 1, from the same bf16 weight buffer that AdamW rewrites every step. It runs through the same job_loop; only the phase table and the task bodies differ.

Batch-1 decoding is a sequence of matrix-vector products: each weight is read once per token and used for one multiply-add. It is bound by memory bandwidth, not math, so its tasks are shaped around streaming weights (llm/b200/megakernel/decode_wide.cuh). One token is 38 phases, 2,225 tasks:

Phase (per token)TasksWhat one task does
QKV, per layer36LayerNorm of the residual (recomputed by every task), then 64 columns of the QKV GEMV; appends K and V to the cache
ATT+WO, per layer36softmax attention of one head over the cache, then that head's slice of the output projection for 256 columns
UP+DOWN, per layer4864 hidden units: up GEMV, GELU, then their contribution to all 768 outputs of the down projection
HEAD784final LayerNorm, 128 vocabulary rows of the tied head, and the best candidate in those rows
SAMPLE1pick the token from 784 candidates, advance the position, write the next token's embedding

Fusing more per task (LayerNorm into the GEMV, attention into its output projection, up into down) cuts the number of phases per token, and each phase boundary is a wait on a counter. Each layer is three phases, not seven. The cross-token dependency is phase 0 of token t+1 on SAMPLE of token t, expressed with delta = -1 exactly like training's cross-step dependencies.

Three details make serving from live weights work.

1. Never read a weight from L1

Training SMs rewrite the bf16 weights every step. If a decode SM had a weight line cached in its L1 from an earlier token, it could keep reading the old value indefinitely, since L1 is not kept coherent with writes from other SMs. All weight loads in decode use a load that does not allocate in L1:

llm/b200/megakernel/decode_wide.cuhlines 105–112
// 16 B streaming load for weights / KV: weak load that does not allocate in L1 (so it can never hit a stale L1 line
// even if the optimizer refreshed the weights earlier in the same kernel; not .nc for the same reason).
__device__ __forceinline__ uint4 ldw(const void* p) {
  uint4 r;
  asm volatile("ld.global.L1::no_allocate.v4.u32 {%0,%1,%2,%3}, [%4];" : "=r"(r.x), "=r"(r.y), "=r"(r.z), "=r"(r.w) : "l"(p));
  return r;
}

The decode and training jobs do not synchronize at all, so a token's forward pass can read some layers before an AdamW update and some after. For a live demo of a model that changes slowly, that is acceptable. The served text gets better as the loss falls.

2. A residual stream in fixed point

The attention-output and down-projection tasks each produce a partial sum for some of the 768 residual entries, and many tasks add into the same entries. Floating-point atomics would make the result depend on the order tasks happen to finish. Decode instead keeps the residual as 64-bit integers in units of 2−30 and adds with integer atomics. Integer addition is associative, so the residual is bit-identical regardless of scheduling:

3. Sampling as a two-level reduction

Each of the 784 HEAD tasks computes 128 logits and keeps its local best candidate twice: once for greedy decoding and once with Gumbel noise added (logit / T + Gumbel), whose argmax is a sample from the softmax at temperature T. The noise is counter-based (a hash of seed, step and vocabulary index), so sampling is reproducible. The 1-task SAMPLE phase reduces the 784 candidates, applies teacher forcing while a prompt is being fed, and writes the next token's embedding into the residual, which starts the next token. In "answer mode" the prompt is fed again after every N sampled tokens, so the dashboard keeps asking the training model the same question and the answers improve.

The output tokens go to pinned, mapped host memory (cudaHostAlloc with cudaHostAllocMapped). The GPU writes them over PCIe while the kernel runs, and the host's HTTP server reads them directly. That is how a kernel that never returns can stream text to a browser.

13Doom as a megakernel job

Doom is the most different of the three jobs: a large, branchy, single-threaded C program with a recursive BSP walk, never written for a GPU. The doom-gpu/ directory compiles doomgeneric with clang's NVPTX backend against a small hand-written libc; varargs are lowered at the LLVM IR level because clang 14 cannot select va_start for NVPTX, and the result is a relocatable device object linked into the megakernel. The engine needs a lot of stack for its recursion, so the host raises the per-thread stack limit to 24 KB.

The Doom partition (8 SMs, 16 blocks) runs its own loop, doom_loop in doom_job.cuh, with its own ticket. Each frame is 6 tickets: one tick task that advances the game by one 1/35 s tic and renders the frame, then 5 copy tasks that each copy 40 rows of the 320 × 200 frame (plus the palette) to pinned host memory. The dependencies are what you would expect: copies of frame f wait for tick f; tick f+1 waits for all copies of frame f, so the next frame never overwrites the buffer while it is being copied.

llm/b200/megakernel/doom_job.cuhdoom_loop, the claim

Two differences from training are worth noticing. The tick has a time dependency as well as a data one: frame f may not start before epoch + f × 28,571,429 ns, read from %globaltimer, which paces the game at 35 Hz. And Doom claims with CAS-after-ready, the scheme training abandoned. At 35 frames per second and 16 contending blocks the CAS cost is irrelevant, and claiming only ready tickets means a block is never parked on a frame that is 28 ms in the future.

Inside a tick, thread 0 runs the game, and the other 255 threads would idle. The repo's fix: thread 0 does not draw wall columns and floor spans itself but queues them, and at flush points all 256 threads execute the queue. One thread owns each screen column, so draws to the same column stay in order and the picture is pixel-identical to serial drawing. The rendezvous uses a named barrier:

doom-gpu/gpu_par.cnamed barrier between the game thread and the workers
// ONE shared barrier instruction: lane 0 (running the game) and its warp-mates (workers) must execute the identical bar.sync instruction or the warp never arrives
__attribute__((noinline)) void gpu_bar(void) { asm volatile("bar.sync 2, 256;" ::: "memory"); }

void gpu_flush(void) {                                   // thread 0 only
  if (!gpu_par_active || (g_ncol == 0 && g_nspan == 0)) return;
  bar(); work(0); bar();
  g_ncol = 0; g_nspan = 0;
}
void gpu_par_worker(int tid) { for (;;) { bar(); if (g_exit) { bar(); return; } work(tid); bar(); } }

Barrier 0 is what __syncthreads() uses, so the game uses ID 2 to stay out of its way. The comment records a real hazard: thread 0 and threads 1 to 31 are in the same warp but run different code paths, and a barrier counts warps, so both paths have to reach the same bar.sync instruction, hence one non-inlined function. This took a frame from 24 ms to 6.7 ms.

Doom's real cost is at compile time. Linking a separate device object needs nvcc -rdc=true, and relocatable device code makes ptxas compile the whole kernel more conservatively: the A100 build's stack frame grew from 552 B to 1,464 B, with more spills, and training slowed by 18%. Stubbing out the Doom call gave the same slowdown, so the cause was -rdc, not Doom. The A100 fast build (llm/ofa_fast) avoids it by merging Doom's PTX into the kernel's PTX and compiling one module. The measured difference between Doom on and Doom off at the same split is within run-to-run noise.

14Blackwell: tcgen05 inside a persistent kernel

On the B200, mma.sync still works but reaches only 13 to 33% of cuBLAS on this model's GEMM shapes. Blackwell's fast path is a different machine: the Tensor Memory Accelerator (TMA) copies tiles from global to shared memory asynchronously, a single thread issues tcgen05.mma instructions that read operands from shared memory through descriptors, and the accumulator lives in tensor memory (TMEM), a 512-column, 128-lane buffer per SM, not in registers. The repo's backend (llm/b200/gemm_tcgen05/gemm_sm100.cuh) keeps the same task contract and the same epilogue math, and reaches 34 to 73% of cuBLAS. With it the training run went from 95.8 s to 48.1 s.

The tile is warp-specialized: lane 0 of warp 0 is the TMA producer, lane 0 of warp 1 issues the MMAs, and all 8 warps run the epilogue. The stages are coordinated with mbarrier objects in shared memory (full[s], empty[s], and one accum):

Dropping this into a persistent kernel exposed three problems that a stand-alone GEMM test never sees.

The TMEM allocation permit

TMEM is allocated with tcgen05.alloc. While a block holds the SM's allocation permit, another block's tcgen05.alloc on the same SM waits until the holder exits. In a normal kernel blocks exit after one tile, so this is invisible. In a persistent kernel they never exit: allocating per tile would serialize the two co-resident blocks of an SM, and could deadlock them. The fix is to allocate once per block, give up the permit immediately, and free at the very end:

llm/b200/gemm_tcgen05/gemm_sm100.cuhonce per block, from job_loop
__device__ __forceinline__ void block_init_tc() {
  if (threadIdx.x < 32) {
    tmem_alloc((uint32_t)__cvta_generic_to_shared(&tmem_base_s), TMEM_COLS);
    asm volatile("tcgen05.relinquish_alloc_permit.cta_group::1.sync.aligned;" ::: "memory");
  }
  tc_fence_before();
  __syncthreads();
  tc_fence_after();
}

Each block keeps 128 of the SM's 512 columns for its lifetime. This is also why the occupancy API reports one block per SM for this kernel: it assumes the conservative case. The host computes the real fit from registers and shared memory instead (section 2).

Two memory proxies

TMA reads global memory through the async proxy; ordinary loads and stores use the generic proxy, and the two are not ordered with each other by default. Here the operands of a GEMM were written moments earlier by another phase's ordinary stores, and the release/acquire handshake of section 5 orders generic-proxy accesses only. The producer therefore issues fence.proxy.async before its first TMA load. The research log records what happens without it in an earlier kernel: bit-exact on 7 of 7 test cases, then wrong on 3 of 66 served requests. Tests that check arithmetic do not exercise synchronization.

Shared memory as the epilogue's staging area

The accumulator leaves TMEM through tcgen05.ld into registers, then goes through a 64 KB fp32 staging tile placed in the now-idle pipeline buffers so that global stores are coalesced, one tile row per warp instruction. The per-element math is the same epi_store logic as the A100 GEMM, and the loss is bit-identical with either backend.

16What it does not buy you

The table above contains the most important caveat: Megatron with Transformer Engine and CUDA graphs trains faster than this megakernel on the same SMs, 43.1 s against 48.1 s. Removing launches is not the same as being fast. Specifically:

  • The GEMMs are not cuBLAS. At 34 to 73% of cuBLAS per shape, and with GEMMs at roughly 80% of training time, the task bodies matter more than the scheduler. A megakernel needs kernel-quality task code, and it gets none of a vendor library's tuning for free, since vendor kernels cannot be called as device functions.
  • Intermediates still go through memory. Every phase writes its output to global memory and the next phase reads it back, mostly from L2. Fusion across phases only happens where the task code does it by hand (epilogues, fused decode tasks).
  • The schedule is fixed at build time. Ticket order is the order of the phase table. A smarter order (critical-path priority, the classic list-scheduling heuristic) would need a different table, not a runtime decision.
  • No preemption. Static SM partitions are how this design meets deadlines. SMs given to serving cannot help training when serving is idle, and vice versa.
  • One register budget and one shared-memory size for every task, and compile-time effects that reach across the whole kernel (the -rdc slowdown).
  • Debugging is harder. A missing fence is a rare wrong answer, not a crash; a missing dependency edge is a hang or a nondeterministic loss. The determinism of every task is what makes such bugs findable: if the loss file changes, the scheduler is wrong.

Where it pays clearly is the combination: running training, serving and a game in one process on one GPU. On the same B200, Megatron (with graphs) followed by vLLM takes about 102 s sequentially and about 59 s side by side on their SM shares (estimated from separate runs), against 52.4 s measured for the 2-stage megakernel doing both at once.

17A checklist for your own

If you build one, these are the rules the code above follows, in roughly the order you will need them.

  1. Launch exactly one resident wave, sized from registers, shared memory and threads, and check it on the device you run on. Anything that waits on another block depends on this.
  2. Write task bodies to a contract: all threads of a block, no blockIdx, shared memory passed in, a barrier at the end. Test each one alone against a reference before it goes near the scheduler.
  3. Claim with one unconditional fetch-add, and keep every dependency pointing to a lower ticket so the claim cannot deadlock. A CAS retry loop on one counter will not scale to hundreds of blocks.
  4. Publish with fence, barrier, atomic; consume with acquire load, barrier. Read data produced in the same launch through L2 (.cg, L1::no_allocate), never through the read-only or L1 path.
  5. Never reset a counter. Make targets a function of the step, and cross-step dependencies fall out of the same formula.
  6. Give buffers to phases, not to time. Per-layer activations remove write-after-read edges you would otherwise forget.
  7. Keep the math deterministic. No float atomics, fixed reduction orders, integer atomics when many tasks must add into one place. Then the loss curve is a test of your synchronization.
  8. Partition by %smid when jobs need isolation or deadlines, and probe the ID space first.
  9. Allocate per-block hardware resources once (TMEM, barriers) and release permits that would block co-resident blocks.
  10. Fence across proxies when an async engine (TMA) reads what ordinary stores wrote.
  11. Instrument from inside. %globaltimer, per-phase busy time and per-step completion stamps cost a few atomics and are the only profiler that sees inside a kernel that never returns.
